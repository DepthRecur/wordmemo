# 用户可见消息分级：错误 / 警告 / 提示

> 定稿：2026-11-20，定义由用户口述给出。**这份文档管"这条消息该是什么级别"**；
> 文案该写什么、灰字能写什么，见 [HANDOFF §10](HANDOFF.md) 的「界面灰字规则」。
>
> 适用对象：用户看得见的一切反馈——右下角 toast、通知中心（铃铛）、导入页的
> 「AI 校验」与「解析提示」、逐文件解析结果、红色弹窗、按钮旁的内嵌提示。
> **改任何用户可见消息前先读这一页**，不要凭手感选红色。

---

## 0. 一句话

**错误 = 某项功能的结果错了、或者功能不能用了。**
**警告 = 出了异常，但功能照常能用、结果也没错。**
**判的是后果，不是"有没有抛异常"、也不是"你觉得严不严重"。**

用户原话：「我对要归类到要抛错的问题的理解是，会导致某项功能结果出错/不可用之类的严重问题的问题；
而抛 Warnings 的则是异常，但不导致功能不可用/出错之类的严重问题的问题。」

---

## 1. 三级定义

| 级别 | 判据（满足任一即算） | 用户要做什么 | 现在的渲染方式 |
|---|---|---|---|
| **错误**<br>error / "抛错" | ① 用户刚发起的**写入类**操作没完成（保存、删除、入库、导入、备份、写复习记录）→ 改的东西丢了或没落库；<br>② 某项功能**整体不可用**（Key 无效/余额不足/没权限/网络不通/磁盘不可写/图片识别没配 Key）；<br>③ 功能"做完了"但**结果是错的**（写坏了数据、写串了库、写成了别的值） | 必须处理：重试、换 Key/模型、去设置、手动改 | 红色 toast + **常驻**在铃铛里待处理（`notify(msg,'err')`） |
| **警告**<br>warning | ① **只读**操作失败，但旧数据/原始状态完好（刷新目录、刷新价格、查音标、复制到剪贴板）；<br>② 功能做完了，只是**结果打了折**（AI 结构化/补充搭配降级、音标缺失、价格未知）；<br>③ 功能做完了，但**内容可疑**，需要人核对（AI 校验提示、OCR 有无法确认的字符、同笔记内重复词条）；<br>④ 提醒类：不拦操作，只是告诉你现状（AI 预算用完、有草稿待处理） | 不必须现在处理；看到了最好核对一下 | 黄色 toast + **也常驻**在铃铛里（`notify(msg,'warn')`）。**常驻是有意的**（2026-11-20 用户要求）：允许用户稍后再看，不替用户判断"这条不重要" |
| **提示**<br>info / ok | ① 操作成功（"已入库"、"已创建"、"已备份到 …"）；<br>② 用户少做了一个前置动作（"先选一个词条"、"先给库起个名字"、"先写下答案"）；<br>③ 纯进度信息（"正在识别…"、"还有 N 份未入库，已切到下一份"） | 无，或按提示补一步 | 灰色/绿色 toast，3 秒自动消失 |

**别把"提示"塞进错误**：用户少做一个动作时，没有任何东西坏掉，红色常驻只会训练用户无视红色。

## 2. 判定顺序（照这五问走）

1. **这次操作有没有把结果写进去 / 做完？**
   - 没做完，且用户有损失（改的没保存、删错了、导入没入库、备份没生成、复习记录没写）→ **错误**
   - 没做完，但**旧数据还在、原始状态没被破坏**（刷新目录失败但旧列表还在、查不到音标但复习继续）→ **警告**
2. **是某个功能整体不可用吗**（没 Key、没权限、网络不通、库打不开、磁盘不可写）？→ **错误**。
   注意："没有 Key"本身是受支持状态（[HANDOFF §5.6](HANDOFF.md)），不要做成常驻红条；
   但用户点了一个必须要 Key 的按钮而失败时，这次操作仍然算错误。
3. **功能做完了吗？只是结果不可靠 / 少了东西吗**？→ **警告**（降级、缺失、可疑）。
4. **只是告诉用户"你还得先做一步"吗**？→ **提示**。
5. **内容是"可疑"而不是"坏了"吗**（AI 认为某个释义可能错）？→ **警告**。
   内容疑点**永远不阻塞**：可以劝、不建议、给"采纳"，但不能拦着入库。

### 五条硬规则

1. **捕获到异常 ≠ 错误。** 如果代码已经降级、功能仍然完成（AI 结构化失败但启发式结果还在），
   对用户就是**警告**，文案里不要把技术异常原样抛给用户当"失败"。
2. **静默失败也要算账。** 没抛异常但结果为空、为错（例如解析出 0 个词条却提示"已识别"），
   按定义属于**错误**，不能因为"没报错"就不报。
3. **一条消息只有一个级别，级别变了文案也要跟着改。** 红改黄的时候别留着"失败"二字
   （改成"没查到 / 这次没刷新成功，可以稍后再试"）；黄改红的时候别只换个颜色就算完。
   写着"失败"的**写入类**消息必须是红色。
4. **错误必须给用户一个能做的动作**（重试 / 去设置 / 换模型 / 手动填写 / 从备份恢复）。
   想不出用户能做什么，多半它不是错误，而是警告或提示。
5. **颜色跟着级别走**：红色只给错误；数量类、状态类信息（"3 处待核对"、"预算已用完"）一律不用红色。

## 3. 代码里怎么落地（通道对照）

| 通道 | 位置 | 现在的级别 | 备注 |
|---|---|---|---|
| toast | `src/renderer/src/App.tsx` 的 `notify(message, type)` | `type: 'ok' \| 'info' \| 'warn' \| 'err'`；**`warn` 与 `err` 都会常驻铃铛**（黄色 / 红色左边框），`ok`/`info` 3 秒消失 | 最常用。**警告就用 `warn`**，不要再拿 `info` 冒充 |
| 通知中心系统条 | 同文件 `syncSystemNotice(systemId, present, message, action?, level)` | `level` 默认 `'err'`（红色常驻）；只是提醒/建议时传 `'warn'`（黄色常驻） | 托盘故障 = err；草稿校验待处理、AI 预算 = warn |
| AI 校验提示 | `ValidationIssue.severity`（`src/shared/types.ts`）→ 导入页「AI 校验」面板、行高亮、`unresolvedErrors` | `error` = 面板「很可能错」（深暖色）；`warning` = 「建议核对」；**整行都只用警告底色** | 这是**内容可疑程度**，不是系统故障；两档都属于警告，**绝不阻塞入库**、绝不用错误红 |
| 解析提示 | `ImportPreview.warnings` / `ImportDraft.warnings` → 导入页「解析提示」面板 | 灰字 `hint` | 放降级说明（AI 结构化/补充搭配失败、跳过校验）、OCR 疑点。**不要**把"结果为空"塞进这里 |
| 逐文件解析失败 | `ImportResult.ok=false` + `error` | 红色汇总 toast | 该文件没导入成功 → 错误；**解析出 0 条也算**（草稿照样留着给用户手动整理） |
| 启动失败 | `dialog.showErrorBox('WordMemo 启动失败', …)` | 红色弹窗 | 应用起不来 → 错误 |
| 考试计划建议 | `ExamPlan.warning` | 黄色提示条 | 建议性质 → 警告 |

### 常驻策略（2026-11-20 定）

`err` 与 `warn` **都常驻**在铃铛里，只有用户点「已处理」或叉掉才消失；`ok` / `info` 3 秒消失。
理由（用户原话）：应当允许用户稍后检查，不常驻用户容易忘掉。
所以"常驻"不再代表"这是错误"，级别只看**颜色**：红 = 功能坏了，黄 = 功能没事但要留意。

## 4. 现状审计（2026-11-20）

按 §2 逐个通道核对过一遍。**✅ 合规的常见大类**：

- 读数据失败（加载今日任务/复习队列/笔记/考试计划/草稿）→ 页面拿不到数据 → 错误 ✅
- 写数据失败（保存笔记/复习记录/学习记录/词条/方向、删除、移动、复制、丢弃、入库、建库/改库/删库、调整顺序、备份、Key 落盘）→ 错误 ✅
- 解析/校验/判分/音标重爬/AI 补充整体失败（功能这次没产出，或导入整体中断）→ 错误 ✅
- Key 无效、余额不足、网络不通、模型拒绝请求（`normalizeHttpError`）→ 错误 ✅
- 启动失败弹窗 → 错误 ✅
- 成功类、前置条件类、进度类（"先选一个词条"、"先给库起名字"、"先写答案"、选择上限、切到下一份）→ 提示 ✅
- 考试计划建议、导入页「建议先核对」提示、笔记详情"有 N 处校验提醒" → 警告 ✅

**❌ 曾经不合规、已在 2026-11-20 改掉**：

## 5. 写文案时别踩的反例

- ❌ "保存失败" 用黄色 → 用户以为存上了。
- ❌ 用红色显示 **数量**（"3 处待核对"、"2 份草稿"）→ 数量不是故障。
- ❌ 把"没选词条 / 没填名字 / 没写答案"当错误 → 这只是在提醒下一步。
- ❌ 静默失败：返回空结果、写了一半、降级成功却什么都不说 → 至少给警告。
- ❌ 一条消息两个级别：「校验完成，但有 2 处错误」——拆成"已完成"+"警告 N 处"。
- ❌ 把技术异常原文直接抛给用户（`SQLITE_BUSY`、`ECONNREFUSED`）→ 先翻译成人话，再看它属于哪级。

## 6. 和相关文档的关系

- **文案写什么** → [HANDOFF §10](HANDOFF.md)「界面灰字规则」。
- **本页管级别（红/黄/灰）**，两者不重叠：灰字回答"我要做什么/会发生什么"，级别回答"这事有多严重"。
- [BUGS-PROVIDERS.md](BUGS-PROVIDERS.md) P-04 的决定仍然有效：**校验批次失败直接抛错、不降级成警告**
  （因为那会让用户以为校验跑过了）。按本文定义，它属于"功能这次没产出"→ 错误，前后一致。
- 无 Key 的定位见 [HANDOFF §5.6](HANDOFF.md)：没 Key 是受支持状态，不做常驻红条；
  只有实际点用了需要 Key 的功能时，那次失败才按错误处理。
- **「允许一个库都没有」**（2026-11-20）：删到最后一个库时，笔记不删，`deck_id` 置 0 = 「未归类」，
  只在笔记库的「全部」里出现，之后可以批量移到新库。所以 UI 里**不要**再把"没有库"当异常或错误提示；
  需要库的操作（如批量移动）给"在下面新建一个"这类**提示**就够了。
