## 0. 一页结论

| 顺序 | 功能 | 工期 | 风险 | 为什么排在这里 |
|---|---|---|---|---|
| 1 | 多供应商（DeepSeek / OpenAI / Gemini / GLM） | **3~4 天** | 低 | 只动 `settings` + `ai` 两层，不改数据结构；直接决定别人拿到软件后能不能用起来 |
| 2 | 多个库 | 3~4 天 | 中 | 改 schema + 一批查询的作用域。**必须在同步之前**，否则同步格式里没有库维度；也是你自己现在最痛的问题（3500 词占满队列） |
| 3 | 便携版 + 自更新（不签名） | **4~5 天** | 中 | 需要仓库 + 打包 + CI + 启动器。先有它，后面功能的修复才发得出去 |
| 4 | 云端同步 | 8~12 天 | 高 | 唯一会改数据模型（稳定 ID、变更日志、加密），必须等前三个把 schema 与发布纪律立好 |

> **进度（2026-11-21）**：① 多供应商 ✅ **完成并冻结**（P0–P3 + 设置页分区 + 模型下拉；DeepSeek / GLM 真机验证，OpenAI / Gemini 未验证）　② 多个库 ✅ **完成并合并 master**（PLAN-DECKS §15）　③ 便携版 🔶 **U0 + U1 完成**（zip + 启动器按需降级 + version.json；U2 自更新/U3 CI 未做，PLAN-UPDATE §10/§11）　④ 同步 ⬜ 未开始

**排序的四个理由**

1. **依赖方向**：同步依赖「数据模型稳定 + 能把修复合规地发出去」，而库是数据模型的一部分（`notes.deck_id`、`decks` 表都要进同步格式）；自动更新依赖「有 GitHub 仓库和打包链路」；多供应商几乎不依赖任何东西。
2. **风险收益比**：多供应商收益最大（没有 Key = 软件一半功能不可用）、风险最小（不改库）；多个库工作量小、痛点最直接。
3. **你的初衷**：每加一个功能都要能**单独测、单独撤**。多供应商和多库用一个 feature flag 就能关掉；自动更新能"不检查"；同步做不到——它改 schema。所以同步必须最后做。
4. **可调换**：多供应商与多个库互不依赖，谁先谁后都行（哪个更急就先做哪个）；但**同步必须排在这两个之后**。

> 不要四个一起做。每份计划末尾都有独立的验收清单，过一份、冻结一份、再开下一份。

## 1. 四个功能共同的约束（每条计划都要遵守）

1. **不引入服务器、不引入账号体系。** 没有租服务器、没有自建后端、没有遥测上报。三家能力分别来自：用户自己的 API Key、用户自己的 GitHub 私有仓库、GitHub Releases。
2. **默认关闭、显式开启。** 新能力上线时开关默认 `false`，用户主动打开。关掉后，行为必须和今天完全一致（这也是回滚手段）。
3. **一次一个分支、一个 PR、一份验收清单。** 完成即冻结，后续只修 bug，不在同一分支上顺手加功能。
4. **schema 只加不删。** `PRAGMA user_version` 单调递增；迁移只允许 `ADD COLUMN` / `CREATE TABLE` / 建索引，不做删列改名；**迁移前必须先备份**（见 §3 的坑）。
5. **三种密钥永不混用**，各自独立存储、独立清除、独立提示：
   - AI Key（各家厂商，1~N 个）
   - GitHub PAT（同步用，只给单一仓库 contents 权限）
   - 同步主密钥（本地派生，**绝不上传**）
6. **隐私边界写进 README 和设置页。** 哪段内容发给哪家厂商（OCR 会发图片、判分会发词条与答案）、哪些内容进你自己的 GitHub 仓库、哪些永远不出本机（Key、密码、日志）。
7. **不许顺手加功能。** 你原话是「更新太多新功能反而违背初衷」。这四份计划里凡是超出范围的想法，一律进各文档末尾的「明确不做」，不夹带。

## 3. 四者的交叉影响（提前钉住，别等踩了再改）

| 交叉点 | 具体约束 |
|---|---|
| 供应商 × 同步 | AI Key 永不进同步快照；每台设备各自配 Key。同步的 `settings` 白名单里必须显式排除所有密钥字段 |
| 供应商 × 更新 | 模型名、价格表内置在代码里，**不做远程下发配置**（避免"更新源被劫持就能改你调谁"）。价格变了就发一个版本 |
| 多库 × 同步 | `decks` 表、`notes.deck_id` 必须进同步格式；库的删除用 tombstone，合并笔记时按 uid 归并。**这就是多库必须排在同步之前的原因** |
| 多库 × 更新 | 库的迁移会动到 `notes` 表，属于"要备份的迁移"，发布时必须在 Release Notes 里标注 |
| 同步 × 更新 | 两套版本号别混：`schemaVersion`（本地库结构）/ `syncFormatVersion`（快照格式）。旧客户端读到新格式必须**明确拒绝并提示升级**，不许静默丢数据 |
| 四者 × 备份 | 更新装完、同步合并前、库迁移前，都要有可回退的 DB 备份 |

**一个已经存在的坑，四份计划里都要顺手修掉：**
`src/main/index.ts:295` 的 `openDb()` 内部就会跑迁移（`src/main/db/connection.ts:17`），而 `dailyBackup()` 在 `src/main/index.ts:308` 才执行。也就是说**升级后首次启动如果迁移失败，手边只有昨天（或更早）的备份**。四份计划都要求改成：`openDb` 之前先判断 `user_version`，若需要迁移则先复制一份 `wordmemo-pre-migrate-<version>.db`，再做迁移。

## 6. 复用调研的结论（已补做，详见 [RESEARCH-REUSE.md](RESEARCH-REUSE.md)）

产品级调研（找「已经做了这个功能的产品」而不是找库）的总结论：**能整段抄的代码只有两个文件**，其余只能抄结构/交互。

| 功能 | 结论 | 许可证 |
|---|---|---|
| 多供应商 | **4 家**（DeepSeek/OpenAI/Gemini/GLM）→ **不装 pi-ai**，自写约 300 行 + 声明式表（字段照 Cline）；模型名走 `/models`、价格走 models.dev + 快照 | MIT / Apache-2.0（只抄字段） |

## 7. 还剩的坑（按「会不会丢数据」排序）

### P0：会丢数据 / 打不开的

| # | 坑 | 后果 | 对策 | 在哪 |
|---|---|---|---|---|
| 1 | **迁移跑在备份之前**：`openDb()` 内部就迁移（`connection.ts:17`），`dailyBackup()` 在 `index.ts:308` 才跑 | 升级后首次启动迁移失败 = 只有昨天的备份 | `openDb` 之前判断 `user_version`，需要迁移就先复制 `wordmemo-pre-migrate-v<N>.db` | 四个计划都要改 |
| 2 | **同步的时间戳没有时区**：`localIso()` 存本地时间、无偏移，LWW 直接比字符串 | 两台设备时区不同 / 夏令时 / 手动改过时钟 → 新改动被旧改动覆盖 | 同步 op 另加 `ts_utc`（epoch ms）；`due_at` 保持本地时间不动 | PLAN-SYNC §3.9 |
| 3 | **批量删除会连带删词条**：`deleteNote` 会 `DELETE FROM items WHERE NOT IN (SELECT item_id FROM note_items)` | 只存在于这批笔记里的词，卡片与复习记录一起没 | 确认框写清「会删掉 N 个词及其复习记录」；批量操作进日志 | PLAN-DECKS §6.3 |
| 4 | **便携版/源码模式把数据放进程序目录**：`index.ts:22-26` 在 `!isPackaged` 时把 userData 设成 `appPath/.data` | 用户覆盖/删除程序目录 = 词库没了 | 便携版必须 `isPackaged=true`；开发模式的 `.data` 绝不能成为用户路径 | PLAN-UPDATE §3.11 |
| 5 | **同步「事件流 + 重放」没有先例** | 重放结果和真实 `cards` 不等价 → 复习进度错乱 | S0 先做 golden test；3 天内做不到 0 差异就走「以卡为准 + 冲突副本」退路 | PLAN-SYNC §5 S0 |
| 6 | **恢复密钥丢失** | 同步数据永久不可解（零知识） | 一次性展示 + 强制勾选「我已抄写」；不做「找回」 | PLAN-SYNC §3.5 |

### P1：功能会错 / 会误导

| # | 坑 | 后果 | 对策 |
|---|---|---|---|
| 7 | **库作用域漏改一处** | 在 A 库刷到 B 库的词，用户觉得"库没生效" | 作用域收成一个 helper；`grep FROM cards/items/notes` 审计；7 个入口各有单测 |

## 9. 验证条件（现实约束与替代办法）

你手上的条件有限，下面把「没法验的」变成「可替代的」，别让它们拖住进度：

| 缺什么 | 影响 | 替代办法 |
|---|---|---|
| **没有 OpenAI / Gemini 的 Key** | 这两家无法真机验证 | ① 4 家共享同一个 `transport.ts`，DeepSeek 跑通就等于传输层跑通；② 用官方文档样例做**录制夹具**跑单测（断网可跑）；③ UI 标「未验证」+ 一键诊断日志；④ README 写状态表，用户反馈后改配置即可，不必发版。详见 [PLAN-PROVIDERS §9.1](PLAN-PROVIDERS.md) |
| **没有 Windows 虚拟机** | 便携版的「解压即用 / 换目录 / 数据不丢」无法在干净环境验证 | ① **Windows 沙盒**（Win10/11 Pro 自带，无需另装系统）：把 zip 拖进去，等于全新机器；② 没有沙盒就**新建一个本地 Windows 用户**，用那个账户跑一遍（`%APPDATA%` 是干净的）；③ CI 用 `windows-latest` 做「打包 + 启动冒烟」 |
| **Ubuntu 虚拟机** | 对 Windows 便携版/启动器没用 | 留给「同步」阶段：在 Ubuntu 上跑一个纯 Node 的合并逻辑测试（不启动 Electron），验证记录级合并的幂等/交换律 |
| **没有签名证书** | 首次运行有 SmartScreen 提示 | 已定不做签名；README 放截图 + sha256 + VirusTotal 链接 |

> 一句话：**能自动化验证的（请求构造、响应解析、合并逻辑、打包）用测试和 CI 覆盖；只有"真机跑一遍"的缺口（OpenAI/Gemini 的 Key、Windows 干净环境）用沙盒/新用户/社区反馈补。**
